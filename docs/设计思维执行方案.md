# 自动旅行攻略 App 设计思维执行方案

## 0. 项目一句话

自动旅行攻略 App 的首个产品方向定义为：

**跨交通联程可执行攻略生成器。**

它不负责下单，而是帮助用户在复杂、分散、真假混杂的旅行信息里，快速生成一份**可执行、可解释、风险透明**的出行方案。

## 1. 阶段一：理解

### 1.1 Persona

| 维度 | 定义 |
| --- | --- |
| 目标用户 | 自由行用户，尤其是需要跨交通联程的人 |
| 典型画像 | 28-40 岁城市白领，愿意为旅行投入预算，但不愿投入大量时间做路线核对 |
| 使用场景 | 海岛、跨境、落地后还要接驳车船、对到达时间敏感的行程 |
| 当前做法 | 小红书、抖音、航司、地图、天气、订票平台来回切换，人工拼接方案 |
| 主要痛点 | 信息过时、联程断裂、夜间到达、预算失控、攻略不可信 |
| 成功标准 | 5 分钟内拿到两套可执行方案，并明确知道风险和取舍 |

### 1.2 Hook Canvas

| 模块 | 内容 |
| --- | --- |
| 触发 | 已决定去某地，但开始做攻略时发现交通链路复杂 |
| 外部触发 | 节假日出游、朋友约行程、看到机票低价、临近出发 |
| 内部动机 | 想省心，不想踩坑，不想反复查资料 |
| 行动 | 输入出发地、日期、预算、偏好，生成两套方案 |
| 即时回报 | 快速得到一份能直接执行的计划，不再自己拼接信息 |
| 长期回报 | 每次复杂出行前都先用它做最后确认 |

### 1.3 JTBD

> 当我要去一个交通链路复杂、信息真假混杂的目的地时，我想快速拿到一份可靠的可执行方案，这样我不用自己在多个平台反复核对，也能降低出行出错的概率。

### 1.4 未来用户

| 用户类型 | 为什么值得做 |
| --- | --- |
| 带老人或孩子出行的人 | 更在意夜达、中转、天气、执行稳定性 |
| 首次出境自由行用户 | 信息辨别能力弱，更需要可信解释 |
| 高频周末短途用户 | 复用频次高，适合形成习惯 |

## 2. 阶段二：观察

### 2.1 移情图

| 维度 | 用户真实表现 |
| --- | --- |
| 看到 | 各平台攻略冲突、评论分裂、交通信息不一致 |
| 听到 | “这家一定要去”“这个路线最省钱”“夜里也能到”，但缺少验证 |
| 说出 | “我怕衔接不上”“这个信息到底准不准”“我不想做那么多攻略” |
| 做出 | 同时开十几个页面，记笔记，对比截图，问朋友经验 |
| 想法 | 最怕不是少玩一个点，而是行程断掉、到地方没法走 |
| 感受 | 焦虑、犹豫、信息过载、怕踩坑 |

### 2.2 AEIOU 观察框架

| 维度 | 结论 |
| --- | --- |
| Activities | 查交通、算缓冲、比预算、看天气、确认餐厅和接驳 |
| Environments | 手机端为主，碎片时间决策，常发生在晚上或通勤时段 |
| Interactions | 用户和多个平台交互，但没有一个产品能统筹全部约束 |
| Objects | 航班页、车船页、天气页、攻略帖、餐厅评分页、备忘录 |
| Users | 一人决策，多人同行；决策者对稳定性负责 |

### 2.3 关键假设

| 假设 | 验证方式 |
| --- | --- |
| 用户愿意为可靠性放弃最低价 | 对比“最低价方案”和“最稳方案”的选择率 |
| 用户接受只给两套方案而非海量列表 | 测试方案页停留时间和满意度 |
| 用户会认真看可信度解释 | 记录风险解释的展开率和点击率 |
| 用户需要一页式执行卡 | 记录导出率、分享率、收藏率 |

### 2.4 领先用户

优先访谈以下人群：

- 刚做过海岛自由行的人
- 去过东南亚或跨境目的地的人
- 经常替全家或朋友做出行决策的人
- 因联程、夜达、信息不准踩过坑的人

### 2.5 WH 问题

| 问题 | 要验证的点 |
| --- | --- |
| Who | 谁最常遇到复杂联程痛点 |
| What | 用户最怕出错的是哪一步 |
| When | 用户在什么时间点最需要这个工具 |
| Where | 用户主要在哪个设备和场景里做决策 |
| Why | 用户为什么不信现有攻略内容 |
| How | 用户当前如何拼出一份“勉强可行”的计划 |

### 2.6 发言棒规则

用户访谈时执行以下规则：

1. 先让用户讲最近一次真实出行经历，不先推产品。
2. 只追问行为，不追问抽象偏好。
3. 不问“你会不会用”，只问“你上次怎么做的”。
4. 每次访谈只挖一个核心痛点，不摊大饼。

### 2.7 UX 同理心结论

用户真正购买的不是“攻略内容”，而是：

- 决策确定性
- 风险透明度
- 出发前的安心感

## 3. 阶段三：定义视角

### 3.1 360 度视角

| 视角 | 需求 |
| --- | --- |
| 用户 | 快速、靠谱、别踩坑 |
| 同行者 | 行程看得懂，能直接执行 |
| 产品 | 聚焦高风险决策，不做交易闭环 |
| 商业 | 先验证高频痛点，再决定后续收费点 |
| 供给侧 | 数据源必须可标注来源、更新时间和可信度 |

### 3.2 九宫格视窗

| 维度 | 结论 |
| --- | --- |
| 过去 | 用户靠零散攻略和个人经验做旅行决策 |
| 现在 | 信息更多了，但可信度更差、拼接成本更高 |
| 未来 | 用户需要一个能整合约束并解释取舍的决策助手 |
| 用户 | 想省时间、怕出错 |
| 市场 | 内容很多，可靠决策工具很少 |
| 机会 | 用“规则 + 解释”建立差异化，而不是做内容堆砌 |
| 痛点 | 联程断裂、夜间到达、预算超支、天气误判 |
| 方案 | 生成两套方案并解释为什么这样排 |
| 收益 | 节省决策时间，降低出错率，提高用户信任 |

### 3.3 雏菊图

产品核心向外延展的 6 个能力：

1. 联程约束处理
2. 风险解释
3. 来源可信度
4. 预算平衡
5. 天气与穿搭提醒
6. 行前执行卡

### 3.4 POV 句子

对于要做复杂自由行决策、但没有足够时间和经验自己核对信息的出行者，他们需要的不是更多攻略，而是一份可执行、可解释、可信的行程方案，因为他们最怕的不是少玩一个景点，而是整段行程出错。

### 3.5 HMW 问句

- 我们如何在不做 OTA 的前提下，仍然成为出发前必用的一步？
- 我们如何把“信息可信”做成比“信息全面”更强的价值？
- 我们如何让用户一眼看懂某套方案为什么更稳？
- 我们如何让导出的结果真的能在旅行当天被拿出来用？

## 4. 阶段四：构思

### 4.1 头脑风暴后的收敛方向

首版只保留 3 个核心模块：

| 模块 | 作用 | 是否首发 |
| --- | --- | --- |
| 方案生成器 | 给出两套可执行联程方案 | 是 |
| 风险解释器 | 说明为什么这套更稳、风险在哪 | 是 |
| 行前执行卡 | 把方案压缩成一页式输出 | 是 |

### 4.2 创新技术应用

| 能力 | 用法 |
| --- | --- |
| 规则引擎 | 先保证硬约束成立，如缓冲、禁夜达、预算红线 |
| 评分引擎 | 在可行方案里做省钱、省心、平衡排序 |
| 来源可信度模块 | 标注来源、更新时间、冲突和置信度 |
| 模板化解释 | 把系统判断翻译成用户能看懂的话 |

### 4.3 创意深化

产品的差异化不是“推荐更多”，而是“说明为什么这条路线更值得执行”。

### 4.4 SCAMPER

| 方法 | 产出 |
| --- | --- |
| Substitute | 用“解释性决策”替代“海量信息堆叠” |
| Combine | 结合交通、天气、餐饮、可信度输出统一方案 |
| Adapt | 借鉴风控思路，把旅行方案当成风险约束问题处理 |
| Modify | 把传统攻略改为一页式执行卡 |
| Put to another use | 结果页不仅用于查看，也用于同行沟通和分享 |
| Eliminate | 去掉社区、游记流、交易功能 |
| Reverse | 不从景点推荐出发，而从“不能出错的执行链路”出发 |

### 4.5 结构化聚类

所有功能需求分成三层：

| 层级 | 内容 |
| --- | --- |
| 必须有 | 行程输入、两套方案、风险解释、执行卡 |
| 应该有 | 可信度标签、天气穿搭、预算提示 |
| 以后再说 | 社区、UGC、订票、个性化长期画像 |

### 4.6 点子沟通表

| 对象 | 传达重点 |
| --- | --- |
| 用户 | 帮你少查十几个页面，拿到真正能执行的方案 |
| 团队 | 先做高风险决策工具，不做内容平台 |
| 潜在投资人/合作方 | 差异化在于“约束求解 + 可信解释”，不是旅游内容竞争 |

## 5. 阶段五：原型

### 5.1 原型类型选择

第一轮原型采用：

- 低保真线框图
- 可点击流程原型
- 文本化结果卡片

原因：

- 当前优先验证决策路径，而不是视觉细节
- 需要尽快做用户测试

### 5.2 盒子与架子

核心页面流：

1. 输入页
2. 方案结果页
3. 风险解释展开页
4. 执行卡导出页

### 5.3 原型工作坊计划

| 环节 | 内容 | 产出 |
| --- | --- | --- |
| 30 分钟 | 团队统一首要用户和场景 | 目标 Persona |
| 45 分钟 | 画输入页和结果页线框 | 页面结构 |
| 45 分钟 | 写 2 套结果示例和解释文案 | 结果模板 |
| 30 分钟 | 设计测试任务脚本 | 可执行测试包 |

## 6. 阶段六：测试

### 6.1 测试流程

招募 10 名目标用户，执行带任务测试：

1. 给出真实旅行需求
2. 让用户使用产品完成方案生成
3. 观察用户是否理解两套方案的区别
4. 观察用户是否主动查看风险解释
5. 观察用户是否愿意导出或分享执行卡

### 6.2 反馈收集表

| 维度 | 问题 |
| --- | --- |
| 可理解性 | 你是否看懂两套方案的差别 |
| 信任感 | 哪些信息让你觉得这份方案可信 |
| 可执行性 | 如果今天出发，你会不会按它执行 |
| 缺失项 | 你还需要哪些信息才敢用 |
| 替代方案 | 没有这个产品时你会怎么做 |

### 6.3 A/B 测试

首轮只做两个轻量实验：

| 实验 | A 版本 | B 版本 | 目标 |
| --- | --- | --- | --- |
| 结果呈现 | 两套方案并列 | 默认推荐一套，另一套折叠 | 看哪种更利于决策 |
| 风险展示 | 风险说明放在结果卡中 | 风险说明折叠到详情中 | 看解释是否会被主动阅读 |

### 6.4 试验表

| 指标 | 目标值 |
| --- | --- |
| 方案生成完成率 | > 80% |
| 风险解释点击率 | > 50% |
| 执行卡导出率 | > 30% |
| 测试后愿意再次使用比例 | > 40% |

## 7. 阶段七：反思

### 7.1 回溯板

| 类别 | 内容 |
| --- | --- |
| 保留 | 规则优先、风险解释、执行卡导出 |
| 停止 | 过早扩展景点内容和社区功能 |
| 开始 | 聚焦一个高痛点细分市场做深做透 |

### 7.2 每周反思问题

1. 用户到底把它当内容工具，还是决策工具？
2. 哪种风险解释最能建立信任？
3. 哪些输入项是用户懒得填的？
4. 哪些输出项其实没人看？
5. 哪个单一场景最值得继续深挖？

## 8. 首版 MVP 功能优先级

| 优先级 | 功能 | 理由 |
| --- | --- | --- |
| P0 | 行程输入表单 | 没有输入就没有后续价值 |
| P0 | 两套方案生成 | 产品的核心承诺 |
| P0 | 风险解释和来源可信度 | 差异化核心 |
| P0 | 一页式执行卡导出 | 形成闭环和复用价值 |
| P1 | 天气与穿搭建议 | 强化出发前可执行性 |
| P1 | 餐饮推荐与争议提示 | 增强落地体验，但不是核心决策点 |
| P2 | 历史行程复用 | 提高复购，但首版可不做 |
| P2 | 用户画像和偏好学习 | 需要数据积累，不能前置 |
| P3 | 社区/游记/交易闭环 | 方向太散，会稀释产品价值 |

## 9. 接下来两周执行动作

### 第 1 周

| 动作 | 目标 |
| --- | --- |
| 明确首个目标场景 | 锁定“东南亚/海岛复杂联程自由行” |
| 约 8-10 个目标用户访谈 | 验证真实痛点和现有替代方案 |
| 画出输入页和结果页低保真原型 | 准备测试材料 |
| 写 3 组真实案例结果卡 | 验证解释是否打动用户 |

### 第 2 周

| 动作 | 目标 |
| --- | --- |
| 完成 10 人带任务测试 | 验证是否能完成决策 |
| 统计点击、导出、复用意愿 | 判断价值是否成立 |
| 砍掉非核心需求 | 保证 MVP 收敛 |
| 确定下一个版本范围 | 只保留能提升“可靠决策”的功能 |

## 10. 最终产品定义

自动旅行攻略 App 的首版，不应被定义为“旅游内容平台”，而应被定义为：

**面向复杂自由行场景的高可靠行程决策助手。**

它的产品原则只有三条：

1. 先保证可执行，再谈丰富度。
2. 先解释为什么，再展示推荐结果。
3. 先解决高风险小场景，再扩展到更大市场。
